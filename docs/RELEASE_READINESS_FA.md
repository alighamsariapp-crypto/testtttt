# گزارش آمادگی انتشار نوین‌نت

**تاریخ بررسی:** ۲۲ اوت ۲۰۲۶  
**دامنهٔ بررسی:** سایت عمومی، پنل کاربر، پنل ادمین، API لاراول و بستهٔ استقرار

## جمع‌بندی اجرایی

ساختار پروژه یک برنامهٔ ترکیبی است: رابط کاربری React/Vite به‌صورت فایل‌های استاتیک در `public/` منتشر می‌شود و Laravel 12 مسیرهای `/api/v1/*` را مدیریت می‌کند. ساختار Apache موجود برای همین مدل مناسب است: دارایی‌های استاتیک و مسیرهای SPA به `index.html` می‌روند و درخواست‌های API به `public/index.php` لاراول هدایت می‌شوند.

بخش سمت سرور اکنون از نظر نحوی، بوت‌استرپ، کش پیکربندی و مسیر، و آزمون‌های خودکار سالم است. **۲۰ آزمون با ۱۱۲ assertion با موفقیت اجرا شدند**. تولید نهایی رابط کاربری و بررسی TypeScript نیز موفق بوده‌اند. فایل‌های قفل Composer و pnpm اضافه شده‌اند تا نصب وابستگی‌ها تکرارپذیر باشد.

> **وضعیت انتشار:** بسته برای بارگذاری فنی آماده است، اما راه‌اندازی نهایی تنها پس از تکمیل مقادیر واقعی `.env`، مهاجرت پایگاه داده، فعال‌سازی درگاه پرداخت و آزمون پذیرش دستی تأیید می‌شود. همچنین بعضی عملیات گستردهٔ رابط کاربری که هنوز فقط در حافظهٔ مرورگر اجرا می‌شوند، باید پیش از اتکای عملیاتی به پنل‌ها به API متصل شوند؛ جدول «موارد نیازمند تکمیل» را بخوانید.

| بخش | نتیجهٔ بررسی | وضعیت فعلی |
|---|---|---|
| سایت عمومی | ساخت تولید و مسیریابی SPA/API معتبر است؛ مسیرهای خدمات اصلاح شدند. | قابل نمایش و اتصال کاتالوگ به API |
| پنل کاربر | ثبت‌نام، احراز هویت API، سفارش‌ها و جداسازی مالکیت آزمون شدند. | هستهٔ API آماده؛ برخی قابلیت‌های UI هنوز محلی‌اند |
| پنل ادمین | مسیرها با Sanctum و نقش‌ها محافظت می‌شوند؛ پاسخ ۴۰۱ استاندارد شد. | هستهٔ API آماده؛ CRUD نمایشی UI باید به API متصل شود |
| Backend Laravel | کنترلر سفارش، پوشه‌های runtime، پاسخ‌های خطا و پیکربندی استقرار اصلاح شدند. | آمادهٔ استقرار پس از پیکربندی محیط |
| Frontend React | TypeScript و build موفق؛ ورود نمایشی در production غیرفعال است. | آمادهٔ build، با هشدار اندازهٔ bundle |

## موارد نیازمند تکمیل پیش از بهره‌برداری عملیاتی

رابط کاربری اولیه با داده‌های نمایشی ساخته شده بود. اقدامات امنیتی انجام‌شده جلوی نمایش نقش و دادهٔ جعلی را در production می‌گیرد، ولی تمام عملیات محلی آن را به عملیات واقعی سرور تبدیل نمی‌کند. بنابراین موارد زیر باید پیش از اتکا به پنل‌ها در محیط عملیاتی تکمیل و آزمون پذیرش شوند.

| بخش | وضعیت کنونی | اقدام لازم |
|---|---|---|
| سبد خرید و علاقه‌مندی‌ها | state رابط کاربری هنوز عمدتاً محلی است. | اتصال افزودن/ویرایش/حذف سبد به `/api/v1/cart/*` و تعریف API سمت سرور برای علاقه‌مندی‌ها. |
| پروفایل، آدرس‌ها و سفارش‌های کاربر | API هسته موجود است، اما همهٔ tabهای UI از API تغذیه نمی‌شوند. | اتصال نمایش و ویرایش پروفایل، آدرس، فهرست/لغو سفارش به `/api/v1/users/*` و `/api/v1/orders/*`. |
| تیکت، کیف پول و نشست‌ها | رابط کاربری محلی است و route کامل backend در این بسته ندارد. | طراحی migration، مدل، policy، controller و client API پیش از فعال‌کردن این tabها. |
| عملیات CRUD پنل ادمین | کامپوننت‌ها بخش زیادی از تغییرات را در state/localStorage نشان می‌دهند. | اتصال محصول، دسته، کاربر، سفارش، تنظیمات و CMS به routeهای ادمین؛ برای routeهای ناموجود API لازم افزوده شود. |
| ورود OTP و Google | UI امکان آن را دارد، اما route و ارائه‌دهندهٔ production کامل نیست. | تنها پس از پیاده‌سازی provider واقعی و نگهداری امن کلیدها فعال شود. |
| درگاه پرداخت | adapter وجود دارد، ولی کلیدها و webhook واقعی تنظیم نشده‌اند. | تنظیم کلیدها در `.env`، endpoint callback، signature verification و تست sandbox/واقعی. |
| دادهٔ اولیه فروشگاه | migrationها موجودند؛ seed production تأیید نشده است. | واردکردن کاتالوگ، دسته‌ها، کاربران مجاز و تنظیمات واقعی قبل از launch. |

> **تصمیم پیشنهادی:** از این بسته برای استقرار staging یا نمایش سایت عمومی استفاده کنید. برای راه‌اندازی کامل فروشگاه و پنل‌های عملیاتی، موارد جدول بالا باید به API واقعی وصل شوند و در staging توسط مدیر و یک کاربر عادی آزمون پذیرش شوند.

## راهنمای استقرار روی DirectAdmin / هاست اشتراکی

### ۱. آماده‌سازی فایل‌ها

فایل zip آماده‌شده را خارج از ریشهٔ عمومی دامنه استخراج کنید؛ برای مثال مسیر برنامه باید `/home/USERNAME/noovinnet` باشد. Document Root دامنه یا symlink `public_html` باید فقط به پوشهٔ `/home/USERNAME/noovinnet/public` اشاره کند. هرگز پوشهٔ ریشهٔ برنامه که شامل `.env` و `vendor` است را مستقیماً به وب نمایش ندهید.

### ۲. پیکربندی محیط

در ریشهٔ برنامه فرمان زیر را اجرا کنید و سپس مقادیر واقعی را جایگزین کنید:

```bash
cp .env.example .env
php artisan key:generate --force
```

حداقل این مقادیر باید قبل از بازکردن سایت تکمیل شوند:

| متغیر | مقدار لازم |
|---|---|
| `APP_URL` | آدرس HTTPS واقعی دامنه |
| `APP_ENV` | `production` |
| `APP_DEBUG` | `false` |
| `DB_*` | نام میزبان، دیتابیس، کاربر و رمز واقعی MySQL/MariaDB |
| `SESSION_DOMAIN` | دامنهٔ واقعی، در صورت نیاز به cookie بین زیردامنه‌ها |
| `SANCTUM_STATEFUL_DOMAINS` | دامنهٔ واقعی، بدون `https://` |
| `CORS_ALLOWED_ORIGINS` | فقط originهای مجاز HTTPS |
| `STRIPE_*` یا `PAYPAL_*` | فقط در صورت فعال‌بودن gateway مربوطه |

پس از ایجاد `.env`، مقدار `VITE_ENABLE_DEMO_MODE` را روی `false` نگه دارید.

### ۳. نصب و پایگاه داده

```bash
composer install --no-dev --optimize-autoloader
php artisan migrate --force
php artisan storage:link
chmod -R 775 storage bootstrap/cache
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

بسته، assetهای frontend را از قبل در `public/assets` دارد؛ بنابراین Node.js روی هاست برای استقرار عادی لازم نیست. فقط اگر کد رابط کاربری را تغییر دادید، روی محیط build معتبر `pnpm install --frozen-lockfile && pnpm build` اجرا و محتویات جدید `public/assets` را منتشر کنید.

### ۴. Cron مورد نیاز

اگر `QUEUE_CONNECTION=database` باقی می‌ماند، در DirectAdmin دست‌کم این دو cron را ثبت کنید و مسیر PHP را با هاست خود جایگزین کنید:

```bash
* * * * * cd /home/USERNAME/noovinnet && /usr/local/php83/bin/php artisan schedule:run >> /dev/null 2>&1
*/2 * * * * cd /home/USERNAME/noovinnet && /usr/local/php83/bin/php artisan queue:work database --stop-when-empty --max-time=110 --memory=128 >> /dev/null 2>&1
```

### ۵. آزمون پس از استقرار

پس از انتشار، ابتدا این موارد را بررسی کنید:

1. `https://YOUR-DOMAIN/api/v1/health` باید JSON با `success: true` برگرداند.
2. صفحهٔ اصلی و یک URL مستقیم مانند `/store` و `/product/SLUG` باید پس از refresh هم نمایش داده شوند.
3. درخواست بدون ورود به `/api/v1/admin/dashboard` باید پاسخ JSON با HTTP 401 بدهد.
4. ثبت‌نام، ورود، ایجاد سبد، checkout و callback درگاه را در staging با دادهٔ آزمون بررسی کنید.
5. از مجوز نوشتن `storage/` و `bootstrap/cache/` و ثبت لاگ مطمئن شوید.

## اقلامی که نباید بارگذاری یا عمومی شوند

فایل `.env`، پوشه‌های `node_modules/` و `vendor/` محلی، فایل‌های log و هرگونه credential را در مخزن عمومی قرار ندهید. `vendor/` باید با `composer install` روی سرور یا در pipeline ساخته شود. فایل zip تحویلی نیز `.env` محلی و `node_modules/` را شامل نمی‌شود.

## یادداشت عملکرد

خروجی JavaScript تولیدشده حدود 929 کیلوبایت خام است و ابزار build دربارهٔ chunk بزرگ‌تر از 500 کیلوبایت هشدار داد. این موضوع مانع build نیست، ولی بهتر است در مرحلهٔ بعد پنل ادمین، صفحات حساب کاربری و صفحهٔ محصول با `React.lazy`/dynamic import به chunkهای جدا تقسیم شوند تا بارگذاری نخست سایت عمومی سبک‌تر شود.
